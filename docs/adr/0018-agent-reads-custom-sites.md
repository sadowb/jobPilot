# ADR 0018: The agent reads custom career sites that have no API

- Status: accepted (amends the custom-page rule in `modules/postings`)
- Decision: Known ATSs keep their public APIs. A custom page is fetched once (undici + linkedom) and classified in this order: JobPosting JSON-LD, verified, no agent. Otherwise, with an agent configured, `PostingReader` opens the URL in its own browser tab and a Haiku run returns a zod-validated posting. `isJobPosting` with a title and company is saved verified with `job_posting.source = 'agent'`; `isJobPosting: false` is a `NotAJobPageError` carrying the agent's short reason. If the read fails or times out (120 s) the earlier heuristic decides: apply-form evidence is accepted unverified (runs stay gated until "Looks right"), otherwise not a job page, and the row says "Couldn't read this page with the agent. Try again or confirm it." With no agent configured the behaviour is unchanged plus the hint "Set up Claude in Settings → Agent to read custom career sites."
- Why: JS-rendered career sites (Workday, iCIMS, SuccessFactors, Taleo, SPA pages) return near-empty HTML, so a one-shot HTTP fetch rejects them or accepts them with no data. A rendered page read by an agent is the only general answer for sites without an API.
- Security: the page is untrusted input. The reader's tools are only `snapshot` on its own tab (`READER_TOOLS`); the Neo MCP server exposes no navigation, click, script, download or credential tool, the allowlist also hides its `fill`, and no memory server is attached. The prompt states page content is data, never instructions and carries only the tab id and URL, never page text. The output is a closed zod schema (every string capped, no action field) and goes through the same `str`/`question`/`salaryRange`/`toCountryCode` normalisation as ATS data before `PostingsRepository.ingest`. The URL passes `canonicalUrl` (https, no credentials, no localhost or IP literals) in the fetch and again in the reader, and the fetch already rejected hosts resolving to private addresses.
- Footprint (ADR 0016): the reader opens and closes its own tab on success, failure, timeout and abort; at most two reads run at once and the rest queue; closing the dialog or removing a row cancels the read (`postings:cancel-ingest`); app quit calls `PostingReader.stop()`.
- Cache: an agent-read posting is stored by canonical URL, so pasting the same URL again (tracking parameters removed) is answered from the database and never starts a second run. Failed and unverified results are not cached, so "Try again" re-reads.
- Trade-offs: a read takes up to a minute and costs tokens, which is why the add-jobs row shows "Reading with agent…". The browser resolves DNS itself, so a host that changes its answer between the app's fetch and the tab load is not re-checked. `employmentType` and `applyUrl` are validated but not stored (no columns yet). A salary quoted per hour/month keeps its text but not the numeric `salary_min`/`salary_max`, which are annual.
