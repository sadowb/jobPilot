# ADR 0021: Chat runtime: streamed turns, typed events, a reducer in the renderer

- Status: accepted (issues #255, #251; PR 1-3 built)
- Context: The first chat (#249) awaited one non-streaming structured JSON turn per send. The owner message and the reply appeared together after up to 60 s, replies were forced into 1-4 sentences, and every turn cold-started a Claude process. The visible text sat inside a JSON result, so nothing could stream.
- Decision:
  1. **Transport.** Sending (`chat:job:send`, `chat:cap:send`) saves the owner message and returns `{owner, replyId}` at once. The reply then arrives as `ChatEvent`s on one broadcast channel `chat:event` (`thinking`, `delta`, `done` with `ok|failed|cancelled` and `ttftMs`, `actions`), zod-validated in main (`emitChatEvent`) and again in preload. Events are keyed by chat (application id or `cap`) and reply id. No chat UI library: IPC plus a small reducer is enough.
  2. **Renderer.** `lib/chat-live.ts` is a pure reducer (`sending → saved → thinking → delta* → done`, plus `send-failed`) over the in-flight state; the saved thread stays in the query cache. The owner message and the typing dots appear before the IPC returns. A failed send keeps its text with a Retry. Events of an older reply id are ignored; the first reply id seen binds the live reply.
  3. **Orchestrator.** `ChatTurns` (main) allows one live turn per chat (a second send is refused before anything is saved, not queued), owns an `AbortController` per turn (`chat:cancel`, app quit), coalesces deltas per 40 ms (the first token is never held back), applies a 120 s timeout, and saves the reply only when the turn ends. Cancel keeps the text already streamed; a failure with no text saves a fallback; a failure after partial text keeps the partial.
  4. **Streaming path.** A `streamText` run (`RunSpec.streamText`) answers in plain text with the SDK's `includePartialMessages`, mapped to `delta` events; no `outputFormat`. Anything the chat does beside answering (Cap's relays) is a separate, cheap, tool-less structured step after the visible reply, emitted as an `actions` event. It never blocks the text.
  5. **Warm process.** `chat:warm` (chat opened) makes `AgentSettingsService` start one tool-less Claude via the SDK `startup()`; the next `streamText` run without MCP servers and with the same model claims it. After a reply one is started again. One spare at most, dropped after 90 s idle (gentle footprint: no process lingers once the owner stops chatting). A run with another model or any MCP server discards it and starts normally.
  6. **Observability.** Time to first token is on the `done` event and logged at debug (no content). Total time, tokens and tool counts are not logged yet.
  7. **Hard rules unchanged.** Chat has no approve, submit or click tool. Owner text, history and job data are data-tagged and never instructions.
- Measured (real `claude`, haiku, short prompt, 3 runs, indicative): first visible text before ≈ 2.06 s (the whole structured result); after, cold stream ≈ 2.15 s, pre-warmed ≈ 0.75 s.
- Measured delivery (real `claude`, tool-less chat turn, SDK `ttft_ms` and per-delta timestamps): the CLI delivers token-level deltas, median ~10 chars, 20-35 ms apart (max gap 0.1-0.9 s), 108-154 deltas for a ~1.4 kchar reply; so delivery is not the choke point. With a warm process `system:init` arrives in ~35 ms and the remaining first-token wait (0.9-1.7 s on a one-line prompt, 2-3 s on Cap-sized prompts) is the API call itself (`sdk_ttft_ms`), so warming removes process start (~0.5-1 s) and nothing else. Thinking is disabled for chat turns (`thinking: {type: 'disabled'}`); no measurable change on haiku/sonnet, kept so models with adaptive thinking never reason before replying. Model: the owner's configured model, `haiku` when none.
- Renderer smoothing: the received text is revealed on animation frames by `createTextDrain` (adaptive: backlog/6 per frame, at least 2 chars; flush on done/cancel; instant under reduced motion), written straight to the DOM by the streaming bubble. The thread view (`LiveView`) excludes the reply text, finished bubbles are memoised, and following the stream is an instant `scrollTop` from a ResizeObserver (smooth scroll only for a new message).
- Known limit: Cap with Mnemosyne installed attaches an MCP server, so its turns cannot use the pre-warmed spare and cold-start (plus an optional recall round trip before answering).
- Context assembly (PR 2, `modules/inbox/chat-context.ts`, pure and tested): the job chat gets a scrubbed profile summary (headline, current role, years, location, wants, education, languages; never contact details), the stored CV text (3k chars), the fill plan, the answers already saved (owner's first), the failure reason and the form read-back. Cap gets facts computed in code from the worker's runs and the Inbox (`computeFacts`: running, queued, awaiting answers, awaiting review, failed with reason, submitted, queue paused) and is told to quote them exactly and never to speculate about itself. Read access for Cap (#251) is delivered as deterministic, read-only context: the full read-out of up to 3 jobs the owner's message names (company, role or id). A typed in-process MCP tool server was not built: any MCP server makes the turn ineligible for the pre-warmed spare (cold start ~0.5-1 s on every Cap turn), and the data Cap needs is bounded and known in code. Reopen if Cap needs open-ended queries.
- Notes vs answers (#256, `notes-precedence.ts`): run prompts list the owner's own saved answers (`ownerAnswers`) and state the precedence owner answers and profile > fill plan > notes; a note/posting conflict is raised once and the answer is final. Enforced in the prompt only, not verified against a real model.
- Preferences (PR 3, `modules/cap/preferences.ts`): a lasting wish about every job (work mode remote|hybrid|onsite, locations, free-text rules) stated to Cap is extracted by the same post-reply structured step as relays (`preferences`, max 3, `work_mode` validated), saved in the settings kv (`chat.preferences`, at most 20; work mode and locations replace, rules accumulate, duplicates ignored) and shown as a chip with Undo (`chat:undo` -> `CapChatService.undo`, idempotent). Saved preferences feed every run prompt (`notesPromptLines`, rank below owner answers and profile, above nothing else) and Cap's own prompt; Cap's computed facts flag queued jobs that conflict with a remote-only or on-site preference (`preferenceFlags`, location text heuristics, unknown location never flags). Preferences are not applied by silently skipping or reordering the queue; the owner sees the flag and decides.
- Not done yet (follow-ups, this ADR is updated as they land):
  - Sequence numbers and replay: ordering relies on Electron IPC preserving main's send order within one window; a reload mid-reply loses the live partial (the saved thread is intact, the partial is saved only at the end). Persisting partials at intervals and an event log with retention is open.
  - `claude -p` streaming-input mode (one process across turns) was not tried; login mode cannot resume sessions (ADR 0016), so history is a bounded window sent in the prompt. A summary of older turns is open.
  - Tool calls as live steps in the stream; automatic queue filtering by preference; chips (relay, preference) are not persisted across a reload (the preference itself is, in the next Cap prompt).
- Consequence: `ChatEvent`, `SendChatResult`, `Channels.cancelChat/warmChat/chatEvent`, optional `AgentProvider.warm`, `RunEvent` `delta`.
