# ADR 0017: Replace liteque with the run table as the queue (no queue library)

- Status: accepted (supersedes [ADR 0003](0003-liteque.md); amends the parallel-run default in [ADR 0016](0016-gentle-footprint.md) to four)
- Decision: A run is queued by leaving its `run` row in `queued`. `ApplyWorker` is a slot scheduler: while not paused or stopping and fewer than `crew` runs are active, it claims the oldest queued row with one atomic `UPDATE ... WHERE id = (SELECT ... LIMIT 1) RETURNING` (better-sqlite3 is synchronous, so two slots cannot claim the same run), then executes it. `crew` is read live from settings. liteque is removed and no queue library replaces it.
- Sessions: each run is a native Claude Agent SDK session. The claim mints `session_id` (kept across claims); the first turn passes `sessionId`, a resumed turn passes `resume`. `claimed_at`, `progress_at` and `attempts` are new columns.
- Restart: JobPilot is single-instance, so a `running` row at startup belongs to a dead process. With fewer than 3 attempts it goes back to `queued`; the next claim resumes the session with a notice ("re-check the page, do not re-type filled fields, never submit"). At 3 it is failed ("interrupted repeatedly"). Nothing auto-submits; the approval gate is untouched.
- Watchdog: every agent event sets `progress_at`. A run silent for longer than `limits.stuckSeconds` is aborted and moved to `needs_you` ("Looks stuck on this page"). It is never retried automatically.
- Why: liteque 0.10.0 `Runner.runImpl` checks `stopping` only before waiting on a slot, so `stop()` could still claim a job (we carried a dequeue override). It recovers crashed `running` rows by lease expiry and re-runs them blindly, we wrote raw SQL against its `tasks` table, and it left an unencrypted queue file in `userData`. The `run` table already holds every fact a queue would persist.
- Evidence this shape works: OpenCode (`restart.ts` max attempts plus a restart notice), Codex (rollout files plus resume), Hermes (executions table, `recover_interrupted_executions`, `progress_at`), Claude desktop (one process per session, `--resume`). None of them use a job-queue library.
- Rejected: `p-queue` and `fastq`. The scheduling is about 40 lines, and the run table already provides persistence, so a library adds a dependency (ESM-only for `p-queue`) and abort/`clear()` semantics we would still wrap.
- Crew default is four (was six): friendlier to 8 GB Macs, still 1 to 32.
- Trade-offs: there is no separate queue to inspect or replay; ordering is `created_at, id`. The 5 s watchdog tick and event-based heartbeat can flag a run whose single model turn is silent for longer than `stuckSeconds`. Resume needs a persisted transcript, which is only written under the private config dir in API-key mode; in login mode (`~/.claude`, forbidden by ADR 0016) a restarted run starts a fresh session with the same notice.
- Cleanup: old `apply-queue.db*` and `memory-queue.db*` files are deleted at startup. Memory consolidation is a plain timer with a persisted last-success time.
