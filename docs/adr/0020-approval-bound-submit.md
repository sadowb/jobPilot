# ADR 0020: Submit only what the owner approved (form-hash-bound approval)

- Status: accepted (issue #68)
- Context: Runs fill a form and stop at `awaiting_approval`. Until now no code path could submit, and agents are refused every submit, send and pay click (ADR 0005, 0018). The owner's logged-in browser makes a submit real and irreversible, so the one path that allows it has to be narrow, checked in code and safe to repeat.
- Decision:
  1. **What is approved.** When a fill ends in `filled`, main reads the form back from the run's tab (`BrowserProvider.formSnapshot`: field labels and values plus the form hash). The approval row stores that snapshot (`approval.summary`) and the hash (`approval.form_hash`). The Inbox shows the snapshot, so the owner reviews what the page holds, not what the agent says it typed. A form that reads back empty is never offered for approval (`needs_you`).
  2. **Binding.** The renderer sends only an `approvalId`. The hash is never an input. Approving a card approves the hash stored on that row, and a refilled form creates a new approval with a new id.
  3. **Fail closed.** `approve` first re-checks consent grants (`agent.prepare()`), then re-reads the live form. A different hash, or a tab that is gone (app restarted), expires the approval, fails the run ("Nothing was sent") and queues a fresh fill, so the owner reviews a new approval. Nothing is submitted.
  4. **The only submit path.** After a match the approval is decided with one conditional `UPDATE ... WHERE status = 'pending'`; of two concurrent approves exactly one wins, the other returns `already_decided`. The winner starts a submit run (`ApplyWorker.detach`, so cancel/quit abort it) whose browser MCP is configured with a `SubmitAuthorisation { formHash, claim }`. Inside `neo.ts` a submit-like click (`SUBMIT_ACTION`) is allowed only with that authorisation, and only after it re-reads the live form (same raw snapshot shape as at approval), requires the same hash, re-finds the ref in that fresh read as a button, and takes `claim()`. Payment, delete, sign-out and similar (`NEVER_ACTION`) stay refused with or without an authorisation; a line matching both is refused.
  5. **At most once, durably.** `claim()` is one conditional UPDATE on `approval.submit_claimed_at`. A retry, a second MCP server or a restart gets `false`. Cancel is refused once approved. After a crash, startup settles an approved-but-unfinished submit from the claim: claimed means "clicked, not confirmed" (run `failed`, warning, never retried), unclaimed means "nothing sent".
  6. **Outcome.** `submitted` (and the application `applied`) only when the click was claimed and the agent reports the page confirmed it. Anything else is a `failed` run with an honest message. The application is never marked applied on a guess.
  7. **Needs you.** The owner's answers are validated against the run's own `questions_needed` (known keys, options, all answered), stored as `application_answer` rows with source `owner`, preferred by `resolveFillPlan`, and the application is filled again.
  8. **Audit.** `approval_requested`, `approval_approved`, `approval_rejected`, `approval_expired`, `submit_attempted`, `submit_confirmed`, `submit_unconfirmed`, `submit_not_sent`, `answers_provided`: ids and a 12-character hash prefix only, never field values.
- Trade-offs and known limits:
  - Success is the click plus the agent's reading of the confirmation page. It is not independently verified (employer email or an ATS API would be).
  - The hash is canonical (sorted id, control type, checked/selected state, exact value; value = everything after the first colon, so URLs and times stay whole) and fails closed: a snapshot with no recognisable input roles has no hash, so no approval and no click. The parser still reads Neo's text snapshot format, which is unverified against a live Neo. The hash covers field values the Neo snapshot exposes. A page that puts volatile text into those fields would drift on every approve and loop through refills; live pages must be checked (not verified against real Neo or Greenhouse yet).
  - The CV shown is the stored version the agent is told to attach with `upload_cv` (Neo's `upload` tool, one fixed path chosen by main). It is not a claim it was attached; the form read-back shows that.
  - An unconfirmed click leaves the application in Up next; Start is the owner's explicit choice after the warning. An "I confirmed it was sent" action is a follow-up.
  - Auto submit mode stays out of scope.
- Consequence: `approval.submit_claimed_at` (migration 0007); `BrowserProvider.mcpServerConfig` takes an optional authorisation and `formHash` became `formSnapshot`.
