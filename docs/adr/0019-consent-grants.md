# ADR 0019: Nothing runs until the owner allows it (consent grants)

- Status: accepted (amends ADR 0016: "detect, never configure" now also means "never use before the owner allows")
- Decision: Onboarding P1 detects the agent (Claude Code, Codex, a custom command) and the browser MCP tool (any MCP, found automatically, no hard-coded port) and shows them on a boarding-pass consent sheet. "Allow both" writes one `grant` row per connection (`kind` agent|browser, `scope` agent_run|browser_tab) after a live test call; a failed test withdraws the grant. Grants are revocable in Settings → Connections (`revoked_at` is set, the row stays as an audit trail; a partial unique index allows one active grant per kind and provider). A custom agent's grant stores the resolved path and its SHA-256, rechecked on every run, so a swapped binary is not granted.
- Enforcement: `gateProviders` (`modules/grants/grants.gate.ts`) wraps the `AgentProvider` and `BrowserProvider` in `main.ts`. `RunsService`, `PostingReader` and the onboarding CV/Cap services only ever see the wrapped pair, so no run, posting read or CV read can start without both grants and no feature needs to know consent exists. Tool-less structured calls (`structuredCall`: no MCP servers, ephemeral, zod output) skip the gate's `prepare`, which also demands the browser grant; their `run` still asserts the agent grant.
- Why: the owner's own accounts and logged-in browser are the blast radius. Consent has to be explicit, scoped, auditable and revocable, and it must hold even if a feature forgets to check.
- Trade-offs: only Claude Code can run jobs today (Codex and custom commands are detected and can be granted, but the run adapter is not built; the UI says so). The browser test is "the tool answers", not a real test tab (opening one needs a URL; upgrade with the MCP discovery work, #196). Existing owners who confirmed Claude before this release get their agent grant backfilled at startup; their browser grant is asked on the next run via Settings → Connections.
